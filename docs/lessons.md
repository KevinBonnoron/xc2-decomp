# Lessons: what clang 3.9 does and which source gives the game's code

Findings accumulated while matching the game. The compiler is the one the project uses (clang 3.9.1, the flags of `tools/check.py`), so each finding describes a mechanism of that compiler, the natural source form that gives the game's instructions, and one or two functions where it worked. A function is named with its game address when the finding depends on it; a commit is a commit of `main`.

How to use this file: when a function is one instruction short, one `csel` too many, two stores swapped or a stack frame of 144 bytes instead of 128, look up the symptom in the headings below before you permute locals. The rules on which forms are acceptable (a local, a `{}` block, a helper, a cast) are in [decisions.md](decisions.md); this file only says which form gives which code.

Two habits come first, because most of the lost hours were spent without them:

- **A record is a hint, not a verdict.** A note that says "forbidden" or "differs in the registers" was written with the rules and the knowledge of its day. Retry the function with today's decisions, starting from what the note measured (instruction counts, the address of the first difference).
- **Compare the arguments before the frame.** A wrong argument can look like a stack-slot or spill problem. When the frame size or a spill differs, first compare the arguments of every call with the game's (which register holds what at each `bl`), then permute locals.

## Switches and jump tables

- **The source order of the cases decides the compares.** In a compare chain the case whose body comes next is tested last, and with four cases the first source case decides the split. Write the cases in the order the game tests them.
- **A jump table is in numeric order, but the case bodies are in source order.** Write the cases in the order of their blocks in the game. A switch whose `default` falls into shared code needs the `default` written where the game has it.
- **The order of the blocks of a table comes from rounded block frequencies.** Blocks that tie in frequency are placed in an order that follows that rounding. When your switch lays its blocks out differently from the game's and the table differs, two levers exist:
  1. the arm order of *another* dispatch in the same function (in `GfMenuObjTitle::ListListener::reciveEvent`, writing case 2 before case 1 puts the blocks of the outer table where the game has them);
  2. separate case bodies in place of grouped labels: `case 0: return X; ... case 0xe: return X;` as separate returns in value order, instead of `case 0: case 0xe:`. The blocks still merge, but the rounded frequencies change. This matched the `getListType` switch inlined in `GfGameObj::removeGameObj`.

  Commit `2a55fec19` (the title list listener, `removeGameObj`, `listenerGfObj`); the comments there give the addresses and the orders.
- **A table lookup is a switch.** A 0xc0/0x80/0x140 table that the game reads with `sub #2, cmp #3, b.hs, sxtw` is a `switch` that SimplifyCFG turned into a rodata lookup table, not a data array in the source (seen in `DrMdoSetup::setupMaterial`).
- **Duplicated tails and shared epilogues.** Several `return` statements in the source give one shared epilogue plus branches. A duplicated tail in the game usually means the tail was written once after an `if`/`else`.

## Stores: merging, pairing and constructor order

The order and pairing of the stores of a constructor or setup function come from five mechanisms, listed in pipeline order. When a function differs by an `stp` or `str xzr` against two stores, or the reverse, or by two stores swapped, check them in this order before changing a type.

1. **MemCpyOpt makes a memset from a run of zero stores.** A run of zero stores (any width; `0.0f` and null pointers count) to constant offsets of one base inside one basic block becomes a single memset when it holds at least 4 stores or 16 bytes. The memset is inserted at the end of the run; the single stores keep their IR order, then the memset (lowered as 8-byte stores in descending address order, after the singles). Inside one run the source order is irrelevant. A non-zero constant store, a load, a call, a store through another base or a block boundary ends the run, so a non-zero store written between zero stores splits the memset. Writing `unknown10 = nullptr; unknown18 = nullptr;` first in `dispose()` gives the game's one 24-byte memset (`GfFieldPitchRollController`).
2. **DAGCombiner merges adjacent constant stores late.** Adjacent constants of equal width (two `i32` into one `i64`) are merged only at the last store of the chain, and the merged node is scheduled after the single stores that follow it in IR order. A `scale` stored before an `alpha` and `emissive` pair in the game means the source assigns `scale` before `emissive` (`CharaEffectPlayer::playAfterImage`); declaration order gives the pair first. Corollary: two separate adjacent constant stores in the game mean the original had something between them, because a load or a call between two stores blocks the merge.
3. **Pre-indexed stores.** The first store whose address `base + c` has more than one use (a GEP also used in another block) becomes `str xzr, [x11, #c]!`. Which store gets it depends on the IR of the other blocks, for example the base that an inlined `create()` uses for its memset.
4. **The machine scheduler keeps the order of constant stores** but moves loads (the GOT vtable load) freely between them.
5. **AArch64 load/store optimisation, after register allocation,** merges two adjacent narrow zero stores into `str wzr` or `str xzr`, and pairs `str`/`str` into `stp` only within a window of 20 instructions. Neither crosses a call or a load or store that may alias (a GOT load always aliases). The game's `strh wzr; ldr x8, [x8, #0xff8]; strh wzr` and `stp w8, wzr` come from something the scheduler places between the two stores. `DrResMdoLodObj::DrResMdoLodObj` needs `unknown1c = 0` written before `unknown18 = 1`, so that the memset lands between them and the pair forms.

Commit `9035089ec` (`GfFieldPitchRollController` constructor, `DrResMdoLodObj` constructor, `CharaEffectPlayer::playAfterImage`). Unsolved: `RchaNode::RchaNode` and `GfFieldCollect::seqWaitDo`, where the game has a break of the zero run that no source form gives.

Related findings:

- **Whether two stores pair depends on the number of instructions around them.** A plain reorder of one condition, with no change of meaning, can change `stp` into two `str` (`CacheDraw::getBuf`, commit `c36bf260c`). When the only difference is an `stp` against two stores, reorder the operands of the nearest condition or the statements before it before you touch a type.
- **A member zeroed after a base or member constructor call is a statement of the constructor body, not a member initialiser.** Initialisers run in declaration order before the body, so a store emitted after another constructor's call belongs in the body (`WorkCpu` constructor, commit `69f5a1391`).
- **Dead-store elimination looks at most 100 instructions back.** In a big function two stores of the same member can both survive, so a redundant store in the game is real source (rulings 5 and P3), and whether adjacent stores merge depends on how much code sits between them.
- **A constructor on a shared struct added only to fix a store order is refused.** Use value-initialisation in the initialiser list instead.

## Keeping a branch the compiler wants to turn into a select

When the game has a `cbz` or `tbnz` where yours has `csel`, `cset` or `cinc`, or yours merges two tests that the game keeps apart, the cause is one of these.

- **Two stores in two arms merge into one store of a `csel`** (InstCombine `SimplifyStoreAtEndOfBlock`, `MergedLoadStoreMotion::sinkStore`) when both arms store the same type through the same pointer. The game's `cbz` with two stores is kept when the arms store different types: `unknown60 = reinterpret_cast<const T *>(bytes + off)` with a member typed `const T *` (T not a byte type) in one arm against `= nullptr` in the other, while a `const u8 *`, `u64` or `void *` member gives the `csel`. Seen in `DrResMdoSeamWrkBase::setupHeader`, `changeMemCall` and `DrResMdoVertex`.
- **Two sign tests kept as two `tbnz`.** SimplifyCFG `FoldBranchToCommonDest` folds `x < 0 | z < 0` only when the second compare is alone in its block. Write `x >= 0 && x < count_x && z >= 0 && z < count_z`: the load of `count_x` between the tests stops the fold (a load through a reference parameter is speculated, a load through `this` is not). `DrIrrVolCascade::getSectorResourceIndex`, `getSectorResource`, `getSectorInstance`.
- **An explicit `n > 0 && !flag` guard** that the game has as the loop guard and one test: write only `if (!isCached) { for (i = 0; i < division; ...) }` (`DebDraw::renderRealSphere`).
- **A scalar declared inside a loop or `if` body gets lifetime markers and a shared cleanup block** that SimplifyCFG speculates into `csel` or `cinc`. Declared before the loop, `break` leaves directly and the branch stays; when the game has a shared block and yours has direct exits, declare inside (`GfAutoTalk::BdatInfo::create`).
- **A branch the game keeps where a ternary argument gives `fcsel` or `csel`:** write an `if`/`else` with two calls or two stores. The same call in each arm where the game keeps the branch matched `pc::StateFieldWall::flushWallType`.
- **A variable initialised with a constant before a branch** (`int kind = 0; if (...) kind = 1;`) can enable clang's hoisting or sinking of code common to two arms. When the game shares code between arms that your source duplicates, or the reverse, look for such a variable. A flag local that gives one shared final store for two branches matched `DrCalcStmListObj::texstm_stmchk_topLast` (commit `be4e531b9`).
- **A bounds or null test of an inlined helper that the compiler loses after the caller's identical test.** When the game keeps the range test of an inlined helper after the caller's merged `&&` (`acc.isValid() && !acc.isTerm() && type < 3`, then the helper that finds the image of a fade layer returns 0 for an index out of range), GVN folds the helper's test if it is written on the same predicate (`if (index < 3) {...}`: the same `icmp ult 3`; the frame is 144 bytes instead of 128). The inverse predicate in the helper, `if (index > 2) return 0;` (or `index >= 3`), keeps the test and matches. `GfMenuObjFade::getFadeColor`, commit `3ae49eb91`.

## Null tests, zero tests and clamps

- **A kept `cbz` on `getComponent<T>()`.** When the game keeps the null test of an inlined `getComponent<T>()` and your build drops it (one instruction short, the `cbz` sitting before the inlined cast: the `getRTTI` call and `isKindOf`), the cause is SimplifyCFG: it deletes the null edge of the phi only when the first user of the component is a load or a store with no call or store before it. The game keeps the `cbz` when the first user is a call. So do not read the component right after `getComponent<T>()`: hand it to a function (a helper taking the component, `const GfComIK &`, as in `getFirstColiObject`), or, for the property component, to a function of internal linkage that takes the owner and returns the component (`getPropertyComponent` in `gf_pc_state_util_field.cpp`). The forms measured and the addresses are in the comment on `UpdatableObject::getComponent` in `updatable_object.h`. Commit `0a7d639aa` (`StateUtilField::setWaterMode`, `StateUtil::setEnableSpineIK`, `changePlacementDownDist`, `resetPlacementDownDist`, `TargetIKPlugin::setup`, `DeadColCheckPlugin::testDead`). Symptom to search for: one instruction short, with a `cbz` before an inlined cast.
- **The zero test of a narrow value.** A `u16` or `u8` BDAT value (`Bdat::getValCheck` returns 64 bits) tested as a bool of a narrow local (`if (v)`, `!v`) gives the game's `and w8, w0, #0xffff; cbz w8`, while `v != 0` is widened by the integer promotion and gives `and x8, x0, #0xffff; cbz x8`. When the game zero-extends the value again later (`and w1, w0, #0xffff`), a widened local declared where the game extends places that instruction. Commit `dce799cf2` (`GfAutoTalk::BdatInfo::create`, `getMapjumpID`, `hasEyeBlink`, `playBGM`; the comments hold the addresses). Symptom: `and x8`/`cbz x8` in yours against `cbz w8` in the game, on a BDAT column.
- **A float clamp done through integer registers.** `fmov` to a `w` register, a compare and a `csel` come from `mm::clampRef(x, 0.0f, 1.0f)`, not from `mm::clamp` or an `if` chain (`GfVolumeFade::setFadeRatio`). Try it on every clamp to [0, 1] whose registers differ.
- **A bare discarded call** (`getEquipOrbMax(blade);`) or dead `isUnit()` calls are written where the assembly shows them (ruling 5). When the discarded name misleads, write the plain function (`sqrtf(...)` instead of `direction.isUnit();`, same bytes).

## Member widths: `u16`, `u8`, bit-fields and flag words

- **Two adjacent 16-bit members read as one word are bit-fields.** When the game reads two adjacent 16-bit members as one word (`ldr w`, then `cmp #0x10000` or `and #0xffff`), they are bit-fields of one 32-bit word (`u32 a : 16; u32 b : 16;`), not two `u16` members (`GfComBehaviorMob::isStateCondMatch`).
- **A flag word read with byte loads.** When the game reads a flag or state word with byte loads and clang widens it to `ldr x` plus `lsr` because the member is a `u32` (a 4-byte member at an 8-aligned offset, next to a member read right after it), the member may be a `mm::mtl::unknown027<32>`, the bit set of `include/mm_mtl/bitflag.h`: its align-4 `this` keeps the narrow load, and the enumerators become bit indices. It fixed `event::Manager::end`, `stop` and `fw::FootPlacementIKSolver::getRaycastUp` (commit `e10c5b530`). See decision 48 for the conditions.
- **An inline test written on a base class** keeps two 32-bit loads where the same access through the derived class has alignment 8 and is widened into one 64-bit load. `event::BouRect` matched once its point test was written on `mm::Rect<int>`, the base. When the game reads two adjacent `int` members with two `ldr w` and yours merges them into one `ldr x`, look at the class the accessor belongs to, and at its alignment, before adding locals.
- **A typed local for a zero-extending access.** `u32 slot = ...` where the member is `int` and the game loads it with `ldr w` (P1).
- **A parameter named by a type but passed in one 64-bit register** can be declared `enum AssetPackValue : u64 {}`; a struct holding one `u64` is the other candidate. Say in the comment which evidence you have.
- **A member whose layout looks wrong because of a union.** A union with a pointer as its only 8-byte member is laid out `{ i8* }`, and a value read from a returned temporary becomes a spilled alloca ranked as a memory operation (see Reassociate below). Putting a `u64` member first changes the layout to `{ i64 }` and the operand order with it.

## Inlined helpers, frame layout and duplicated source

- **A temporary and a braced local are not the same frame.** `f(Type(...))`, `Type t(...); f(t);` and `{ Type t(...); f(t); }` give different stack slots and lifetimes. Named locals in a `{}` scope share stack slots; temporaries with a destructor do not. Choose from the slots the game reuses (ruling 3).
- **Containers carry their asserts.** Inlined containers (`FixStr`, `Vector`, `FixedVector`) bring their asserts: the file and line constants in the code tell you which header and method the game inlined.
- **A library built against older templates keeps the template's symbols.** When one area was compiled against an older container or singleton than the rest of the game (`skt`, decision 56), a copy in another namespace renames every symbol the game shares (`mm::mtl::PtrSingleton<skt::CommandManager>`: vtable, `sys()::s_instance`, two destructors). A full specialisation of the template for the area's own type keeps the names and drops the asserts (`PtrSingleton<skt::CommandManager>` in `skt/command_manager.h`); a container with no symbols of its own (`FixedVector`, all inlined) can live in an area namespace. The members it calls must keep their game symbols (`mm::mtl::copy`). Pushing onto a `FixedVector` of 16-byte elements without the assert still reloads `m_size` after the element stores, as the game does (`recvCommand`, `recvBinary`).
- **An allocate-then-free helper that tests its allocator unswitches the loop.** `if (param != nullptr && allocator != nullptr) { param->~CommandParam(); allocator->deallocate(param); }` after an unguarded `if (param->unknowna08 != nullptr) { allocator->deallocate(param->unknowna08); ... }` gives the game's two copies of the queue-draining loop (allocator null and not) in `CommandManager::updateCallback`; without the `param != nullptr` the null copy keeps the clear and the second `deallocate` too. `PortInfo::destroy` has the null test of the front element around both and the allocator test only around the last two calls. Members set in a constructor body, in the game's store order, avoid the merged 64-bit store of two adjacent initialisers (`CommandManager::CommandManager`: 0x314c, 0x3150, 0x3154, then the flag).
- **Records that say "reinline" are often wrong about the cause.** Before writing a body out, find which *member* each compare reads: the four `AssetPackInfo` functions matched with plain loops and plain calls once the right member was compared (`unknown10` of the two packs, `m_assetType.unknown08`).
- **Measure the call form before writing a body out twice** (ruling 8, P4). Several "re-inlined" records were stale: `GmkRoutedMapObj::canPopGobInst` and `canDepopGobInst`, `GfDataParty::isActivateMember` and `GfMenuObjHanaCustom::EquipListListener::reciveEvent` match with the plain call. `DrResMdoTexList::texStmUpdate` differed from the call form only in the order of two loop counters, which a pointer-walk loop in the callee (`for (T *p = begin; p != end; p++)`) fixed for all three users. Compile the call form first; try the pointer-walk loop in the callee when only the loop counters differ; write the body out only when the call still does not match, with the instruction counts you measured in the comment (a count copied from an old note is refused).
- **An existing helper beats a written-out repeat.** The twelve `createFrom*` functions of `GfMenuReference` call `createFromCoverter` (clang inlines it, same instruction counts), which removed five "call it instead" findings of the quality gate. Look in the class and its neighbours for a function that already does it before writing a block a second time.
- **Genuine duplication exists, and is recognisable.** A helper holding the block gets simplified on its own before it is inlined (its branches become selects), which the block inside the caller is not. When the helper form is always a few `csel` away and no flag or unit grouping changes it, the source repeated the block: the six `IDColiGrandObj::test*` callback blocks, `VoiceManager::playAuto` and `preloadAuto` (the `Auto` variants repeat the body of `play` and `preload`), the 0x103 event branch of `GfMenuObjItemList2::ItemListListener::reciveEvent`. In `playAuto` the call form `return play(path, delay, event)` gives 26 instructions where the game has 159, because `play` costs 615 against a threshold of 275; the repeated body puts `wav(path)` after the null test, where it costs 250 and is inlined. `playAuto` is defined before `play` in `voice_manager.cpp`, so that its first reference places it where the game does (commit `502177a9d`).
- **A helper of another class can give the entry block of a whole family.** In `GfDataBlade` it was `GfDataAchievement::getAchievementType`, inlined at the top of each function (commit `bddb557d7`). When several functions of a class share an entry block that no source shape reproduces, look for a small function of a neighbouring class that all of them call, define it where they can inline it, and retry the family.
- **A shared UI block that the game inlines as a static helper.** The listener blocks that fade an object in or out with a `GfMenuObjUtil::CtrlParam` and a `ui::UIObjectAcc` (set the object visible, fill the `CtrlParam`, `startCtrl`) are often inlined static helpers, not statements of the listener. The symptom is the `CtrlParam` stack slot sitting above the accessor of the caller (the helper's alloca lands before the caller's locals), together with the same block repeated in several listeners of the game. Write the block once as a file-local helper taking the handle and call it from each place; a string local that the game puts in the same slot as the `CtrlParam` goes in a `{}` scope. Commit `7106fde12` (`gf_menu_obj_balloon.cpp`, the `SelMoney` and `Box` listeners). Try it on every listener whose frame or `CtrlParam` slot differs.
- **An inlined matrix inverse is one call.** A function whose assembly shows the in-place inverse of an `mm::Mat44` (the 2x2 minors of rows 2 and 3 building the signed first column, the determinant, the assert `mm::abs(det) > MM_FLOAT_EPSILON` at line 2993 of `mm_mat44.h`, the twelve other cofactors, then every element multiplied by `1.0f / det` and the matrix assigned back) calls `Mat44::unknown012()` in `include/mm_math/mm_mat44.h`, always inlined; do not write the cofactors again. It matched `fw::CameraLayer::getMtx`, `event::PosAxis::calcOrigMatInv`, `event::TarAxis::calcOrigMatInv` and the `event::CamFree` users (commit `03ff2e873`). The comment on the helper lists the forms that did not match.
- **A call the compiler erased still names a function.** When the compiler erased what a call was used for, the unit still tells which function was called: clang emits the functions of a unit in the order of their first reference, so compare the game's address order with yours (see the next section).
- **Out-of-line copy less merged than the inlined copies.** When the game's out-of-line copy of a function is less merged than the copies inlined in its callers, one source gives both if a step can only be folded by GVN: read through the iterator or the member each time instead of through a local.
- **Search loops.** Loops over an iterator (`for (it = list.begin(); it != list.end(); ++it)`) instead of loops over `Node *`, and a search loop written with `continue` (`if (p == nullptr) continue; if (cond) return p;`), are the forms that matched.

## Translation units, callee placement and inline cost

The game was built as large unity files, and clang emits a function in the object where it is first *referenced*, not where it is defined. Both facts decide which functions are inlined and in which order they come out.

- **Unity units.** The game's `event` code is one unit; most of `monolib_mm/source/dr` is at most a few units; `gf/data`, `gmk`, `device`, `scn` and `cloud` likewise. Where the repository already groups the files as the game did, an ordinary call is inlined exactly as in the game and nothing has to be written out. Splitting a unit loses functions (taking `voice_manager.cpp` out of `event.cpp` makes 13 functions stop matching, including `TextManager::play` and nine `VoiceManager` functions). Merging per game unit is safe wherever it compiles: 20 of the 24 game units that the tree still split were merged in a trial with no function lost. The units are bounded by the `_GLOBAL__sub_I_*` initialiser functions, which clang emits last in a unit, and by first-reference order (a strong function of file B called earlier by file A sits inside A's block when A and B are one unit).
- **An "inlines X from another file" blocker is usually a unit problem.** Of 50 blockers that named the function the game inlines, 30 had that function in another root of the tree but between the same two end-of-unit markers of the game.
- **Include order inside a unity file follows the game's address order.** The functions of `window.cpp` and of four `dr` unity files are emitted in the game's order because their includes are.
- **Key function.** An implicit destructor, a thunk or an inline virtual is only emitted with the vtable, in the unit that defines the class's first out-of-line virtual. Match that function and they come by themselves; check thunks by name with the unscoped `check`.
- **Emitted by its user.** An implicit copy constructor or a template instantiation exists only where another function uses it.
- **Inlined callee.** When the game inlines another game function into a caller, that function must be defined before its caller in the same unit and match by itself (or, when no call form matches, be written out under ruling 8).
- **Erased argument (ruling 6).** A call that leaves a register unset means the callee is defined in the same unit and never reads that parameter. Keep the parameter (the mangled symbol proves it) and pass the natural value; compare `ml::DrMdoAnim::calcPlaneMatrix`, whose unused `this` is erased the same way.
- **Declaration only.** A declaration with the signature of the mangled symbol, used by your code, is allowed while the body of that function is still a target.
- **Inline cost.** clang 3.9.1 inlines a callee when its cost is below 275 (325 with the `inline` keyword, and 50% more while the callee is one basic block). The cost is 5 per IR instruction that is not free (constant GEP, phi, bitcast, unconditional branch, the single `ret` and `zext i32 -> i64` are free; `zext i16 -> i32` costs 5), plus 25 per call inside the callee and 5 per argument of that call, minus 5 per argument at the call site. A function can be a few units off the threshold because of IR that the machine code does not show: `ml::DrEnvironmentAnim::getHermiteAttr` cost 275 against 275 because of one `zext` of the key count that appears twice in the IR (`ldrh` already extends); reading the count into a local right before the loop (`int num = inf->unknown0e;`) lets clang hoist the two as one, the cost falls to 270, and the function is inlined 26 times and still emitted without an `inline` keyword. No threshold reproduces a game that inlines one call site of a function and not another: in `GfMenuObjItemList2::ItemListListener::reciveEvent` the two sites cost 430 and 435 against 412, a threshold of 290 inlines the wrong one, and only the written-out block (ruling 8) matches.
- **Never hide an unmatched function.** A function that does not match is removed from the tree and its draft is kept elsewhere. `inline`, `static`, an anonymous namespace or a renamed copy used so that `check` does not see it are refused (decision 41 is the narrow exception: the game itself inlines the body into a caller that matches).

## Operand order: Reassociate

The order of the operands of `fadd`, `fmul`, `add` and `or` is set by clang's Reassociate pass, even for floating point without fast-math: for every commutative operation it calls `canonicalizeOperands`, which puts the lower *rank* on the left (ties keep the source order). No expression is reassociated; only the two operands of each node are sorted, and later passes do not undo it.

Rank:

- constants 0, function arguments 3, 4, 5...;
- every instruction that may touch memory (loads, stores, calls, PHIs, allocas) gets `(index of its block in reverse post-order + 3) << 16` plus 1, 2, 3... in program order, so a load's rank is its position among the memory operations of the IR at that time (after SROA, inlining, EarlyCSE, JumpThreading, InstCombine and SimplifyCFG, before GVN and LICM);
- any other instruction: the maximum of its operands' ranks plus 1.

So `rank(expression) = rank(its latest memory leaf) + its depth`. A freshly loaded value is almost always lower than a computed chain of depth 8 built from loads just before it, and a later block always outranks an earlier one. What this means in source:

1. **Evaluation order of two loads:** the load emitted first has the lower rank and goes left (`a.x * b.x` with both loads: `a` left). clang evaluates the right side of `x op= rhs` before the load of `x`: `unknown50.y += call()` is `fadd(call result, load y)`, while `unknown50.y = unknown50.y + call()` loads `y` before the call.
2. **A value read from a temporary that SROA cannot promote** is a load at its position, not an SSA value of depth + 1. The union `Bdat::uVal` has a `const char *` member and so is laid out `{ i8* }`; reading `.valueF32` of a returned value is a spilled alloca until GVN, ranked as a memory operation. Declaring a `u64` member first (layout `{ i64 }`) keeps the value in a register (`fmov s0, w0`) and gives the game's order (`gmk::GmkClimbing::updateIconPos`).
3. **PHIs.** JumpThreading turns a load at the front of a join block into a PHI when both predecessors store or load it (only if the first instruction of the block is a load: a GEP in front stops it). The PHIs of a block are created one after the other and each new one is inserted at the front, so the last created has the lowest rank: `x`, `y`, `z` loaded in that order give PHI ranks z < y < x. A loop-free `if (len <= eps) v = zero; else v = v * scale;` followed by per-component use is the typical source (`mm::Plane::unknown001`, `idcoli::IDColiUtilColiResult::setStockBox`).
4. **Stores and lifetime markers count as memory operations:** a store between two loads adds 1 to the later load.
5. **A temporary kept in memory by a pointer-compare use does not survive:** `Vec3::operator=(Vec3 &&)` has `if (this != &vector)`; InstSimplify folds the compare while inlining and SROA then promotes the temporary.
6. **An accumulation through a phi** (a loop that LoopUnroll removes) gives `add new, old`; a straight-line sum gives `add (a + b), c`.
7. **Integers go through the same canonicalisation.** An `or` chain is flattened and sorted by rank (lowest first, ties keep the source order). A condition such as `flag`, `queue`, `size` tested in this order may come out as `size`, `queue`, `flag` whatever the source order, because phis outrank a flag compare that depends on a load.
8. **The allocation order of two local live ranges in one block follows their definition order in the code before register allocation** (earlier definition, lower register). Passing `group + 1` at the call instead of a local holding `group + 1` puts the load before the add.
9. **A loop counter swap in a Bdat reader** was fixed by declaring `i` before `count` (and `rank` before `i`).

Examples:

- `VerticalData::VerticalData()` and `GfEnvProperty::GfEnvProperty()`: `normal.x/y/z` are PHIs (ranks z < y < x) and the position components are plain loads after them, so every `normal * position` comes out `phi, load` and the sum `(x+y)+z`. The game has `fmul(position, normal)`, `fadd(y, x)`, `fadd(z, sum)`: the ranks you get when the position values are *also* PHIs created after the normal ones. No source order of the dot product changes a rank. Not matched.
- `PlayerCamera::resetClimb`: the game has the chain on the left, which needs the load of `unknown100.x` at least 7 memory operations after the chain's last leaf. The only structure that gives chain-first for every component is "chain stored to the member, member reloaded with the base load after it" (`+=`), which needs the reload more than 6 instructions after its store (InstCombine forwards the stored value within 6). Not matched.
- `DrMdoSetup::setupMaterial`: `((A|B)|C)|D` in the game against `((A|B)|D)|C` in ours, because `C` (select over `and`, `icmp`: load + 4) always outranks `D` (`lshr`, `and`: load + 3). All 120 orders of the five tests failed. Not matched.
- A sum written before an image guard (`technique->unknown1c + technique->unknown24`) is an `add i32` in the join block that a second InstCombine sinks to the top of the guard's preheader; the game has it at the end of the preheader, where LICM puts what it hoists. Declaration order decides the operand order of the add Reassociate rebuilds.

## Loop strength reduction (LSR)

LSR chooses which induction variable and base pointer a loop keeps in registers, and it does not follow any rule that source can express directly. When a loop differs in an `add`, a hoisted `base - 1`, a third counter or a `csel`, and the rest matches, the cause is LSR and the forms to try are about the *shape* of the loop and the accessors, not about the arithmetic.

- **Pointer-walk loops.** A loop `for (T *p = begin; p != end; p++)` in the callee fixed a function that differed from the call form only in the order of two loop counters (`DrResMdoTexList::texStmUpdate` and its three users).
- **The exit test of `mm::mtl::copy<T>` (not matched).** The game's out-of-line `copy<skt::CommandManager::PortInfo>` (0x7100984c5c) and `copy<gf::GfMenuObjOperationInfo::InputObj>` (0x71004a27dc) keep the pointer-walk loop's trip count as `sub x21, last, first` in the preheader and test `cmp x21, x28` on a byte index; the template's `while (first != last) { *result++ = *first++; }` gives `subs x28, first, last` shared with the guard, `add x21, x21, #size` and `add x8, x28, x21; cbnz x8` (84 instructions against 85; the rest of `PortInfo`'s copy matches). Pointer loops of every spelling, `first < last`, an end pointer `result + (last - first)` and index or count loops (the exact division by the element size stays as a multiplication by its inverse) do not give it. A function that needs the copy out of line (`CommandManager::removePort`, explicit instantiation) waits for it.
- **The inlined `FixStr` reverse search** (about 33 game functions: `PathUtil`, `GfMenuMapInfo`, `normalizeFileName`, `makeFullPath`...) keeps `mData - 1` hoisted. About 600 natural forms were tried (signed and unsigned counters, `base[i]`, `s[i - 1]`, pointer or reverse-iterator loops, select or phi bases): all give the LSR form, a third counter or a `csel`. What matches is `c_str()` and `length()` accessors (a call in the found block keeps SimplifyCFG's two-entry-PHI folding from speculating the found block's arithmetic into the loop), a `do { } while (--i != 0)` loop behind a `length() != 0` guard (the second loop then has a preheader that falls through to its header, so early tail duplication does not apply), and a base computed through an integer round trip. One helper then matches 17 functions byte for byte across four libraries (commit `1576fa595`; the full list of forms is in the comment in `include/mm_mtl/fixstr.h`). The integer round trip is accepted only there (decision 55).
- **`FixedObjectAllocator<FileHandleTh, 640>::allocate`** matches only with the object addressed as a byte index into the storage and the loop bound read through a raw byte offset of `this`; both are chosen for the LSR register, not shown by an access, so nothing lands (decision 53).
- **A named single-use local in a loop swaps registers.** Locals such as `number = i + 1` or `slot = i - 1` swap the registers of a loop: write the expression at its use, unless the assembly shows the value computed once and kept (P2).

## Compiler flags

No compiler flag is missing or wrong. 42 flag settings were run over the whole tree; none gained a function, and every one that changes code loses some. Facts worth knowing:

- The inline thresholds are 275 and 325 exactly: 270 loses 113 functions, 280 loses 159; a hint threshold of 300 loses 122 and 350 loses 77.
- `-O3`, `-fno-strict-aliasing`, `-mno-implicit-float`, builtins on, no fast-math component: each opposite loses tens to thousands of functions, in every library.
- The game text holds no `fmadd`, `fmsub`, `fnmadd` or `fnmsub` and no vector `fmla`: floating-point contraction is off, and there is no auto-vectorised code in any library (`-mno-implicit-float` already turns the vectorisers off).
- The target is the Cortex-A57 (`-mcpu=cortex-a53` or `generic` lose more than 26,000 functions), frame pointers are kept, code is position-independent with default visibility (calls and data go through the PLT and GOT, as in the game: `-fvisibility=hidden` loses 13,000), exceptions are off, RTTI is off, and thread-safe statics are on (the guards are in the game).
- A per-symbol `__attribute__((visibility("hidden")))` that makes a table match is refused (decision 43): the library is not hidden as a whole.
- The VM (`vm/yvm2.cpp`) is compiled like everything else; with `-O2` it loses functions that need an inline at cost 255.

## Locals and scopes

What changes the code, and what to do about it:

- **Locals that only steer code generation are dropped.** Each local you keep must place a call, a load or a computation that the assembly shows (P2), and its comment says which; try the function without it. A single-use local where the inline form also matches is refused: check both.
- **A named variable can change code under `-g`.** The project compiles with `-g`, and a named variable leaves a `DBG_VALUE` in the machine code. That is invisible in the IR and in register allocation, but it can change the machine passes that run after them: `AArch64A57FPLoadBalancing` assigns the chain of an `fmul` to `s0` or `s1` differently when a `DBG_VALUE` sits between the `fmul` and its store (the game's party-map save helper at 0x71003558e8, decision 57), and a dead `u32 move = 0;` decides whether a `mov w0, wzr` is hoisted (238 against 240 instructions with `-g`, no difference without it: `GfMenuObjHana::moveCharSubMenuIn`, decision 44). Before you dismiss a local as "register allocation only", compare the function with and without it under `-g`; if the difference is a debug-value effect, decisions 44 and 57 apply.
- **Symmetric natural forms first.** When two parallel expressions or two branches are written differently only because a search found that form (the split line first in one branch only, the translation added last in one of two projections), try the symmetric natural form first. It matched in every case tried and replaced the asymmetric one (P4).
- **Loop or helper before repeats.** A repeated statement is replaced by a loop or a helper whenever that also matches: measure the loop or helper form before writing repeats out, and say in a comment, with both instruction counts, when it does not match (ruling 8; decision 42 for a function that mixes both).
- **`continue` and `||` over negated tests,** when both match: write `if (!usable) continue;` and `a || b`, not `if (usable) { ... }` nests or `!(!a && !b)` (`GfGameTarget::setTargetNearest`).
- **The permuter is a locator, not an author.** Use it briefly to find the few spots that move the score, then reduce its output by hand to the smallest natural change and throw the rest away. A permuter body is never committed as is.
- **Refused forms, do not repeat:** a member retype that breaks another matched function; a new constructor on a shared struct added only for a store order; a partial class without an evidence comment and `offsetof` assertions; a helper without the exact marker line, or with wrong instruction counts in its comment; any change in a reserved area or under `tools/` to make a function match (leave the function and report it).
- **Comment the evidence.** A local: which call, load or computation it places, with the game address. A statement without effect or a repeated store: the address of the operation in the game. A scope: that the stack layout shows the lifetime ends there. An erased argument: that the game never sets the register. A written-out body: the function it repeats and the instruction counts of the call form. A one-user helper: the marker comment, the forms tried without it, the address of its user. A retype: the game accesses (function and address) that show the type; update every user and keep `check` green.
- **Type changes follow the accesses.** A type that another matched function contradicts is not proven (P1). Members that the game zeroes or stores as a unit with one 64-bit store form a sub-object (decision 20).
